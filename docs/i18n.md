# Internationalization (English / Arabic, LTR / RTL)

## Rules

1. **No user-facing literals in components.** Use `t('namespace:key')`. The lint rule
   `pos-local/no-untranslated-jsx` fails the build for JSX text and text attributes
   (`placeholder`, `aria-label`, `title`, `alt`, `label`) that contain letters.
2. Every key exists in **both** `en` and `ar`. `packages/i18n/src/resources.test.ts` fails on
   any missing key, extra key or empty string. English is the reference shape for TypeScript
   key checking.
3. Every API `ErrorCode` has a translation under `errors:<CODE>`; the same test enforces it.
4. Menu content (names and descriptions) is **data**, stored in `nameEn/nameAr` columns. Show it
   with `pickLocalized(entity, 'name', locale)`, which falls back to English.

## Namespaces

`common` (actions, states, validation), `errors`, `auth`, `admin`, `menu`, `orders` (channels,
statuses, totals; shared by the POS and admin), `pricing` (taxes, discounts), `floor` (tables)
`pos`, `payments` (methods, tender, refunds, shifts, cash drawer, daily summary) and `receipt`
(printed receipt labels), `kds` (kitchen display) and `customer` (the customer website: storefront,
cart, checkout, order status; customer-facing order statuses differ from the staff labels in
`orders`). Inputs for localized data declare their own
`lang`/`dir` (`LocalizedFields`), so Arabic is typed RTL even in the English UI and vice versa.
Fixed-height controls use `leading-normal`, because the taller Arabic body line-height would
otherwise clip glyphs.

Receipts print in the operator's language. They are drawn on a canvas, so the browser shapes
Arabic and lays out RTL lines; the bitmap is then sent to the printer (see
[ADR 0009](adr/0009-payment-providers-and-raster-receipts.md)). Thermal printers' own Arabic
code pages are never used.

## Direction

- `applyDocumentLocale(locale)` sets `<html lang dir>`. Layout mirrors because components use
  **CSS logical properties only**: `ms-*/me-*`, `ps-*/pe-*`, `start-*/end-*`, `text-start`,
  `border-s/e`. Physical `ml/mr/pl/pr/left/right/text-left/text-right` are not used for
  layout.
- Directional icons (chevrons, arrows, "back") flip with the `rtl:` variant
  (`rtl:-scale-x-100`). Non-directional icons (search, close, check) do not flip.
- Numbers, codes, SKUs and prices inside Arabic text are wrapped in `.ltr-nums` to keep digit
  order and use tabular figures.
- Radix primitives get the direction through `DirectionProvider`.

## Numbers, money and dates

- `formatMoney(minorUnits, currency, locale, { digits })` formats exact decimal strings through
  `Intl.NumberFormat` (no floats). Tenants choose Latin (`latn`, default) or Arabic-Indic
  (`arab`) digits.
- `formatDateTime(isoUtc, timeZone, locale)` converts UTC to the **location** timezone at
  presentation only.
- Numeric inputs accept Latin digits. Money inputs are parsed with `parseDecimalToMinor`, which
  rejects more decimals than the currency allows instead of rounding.

## Pluralization

i18next uses `Intl.PluralRules`. Arabic has six plural categories, so Arabic plural keys need
`_zero`, `_one`, `_two`, `_few`, `_many` and `_other` suffixes where counts are shown. The
resource test compares languages by **base key** and requires every plural category each
language's `Intl.PluralRules` defines. For example, `menu:modifierGroups.count` renders
"خياران" for 2 and "11 خيارًا" for 11.

## Dynamic keys

Static keys are type-checked (`i18next` `CustomTypeOptions` in each app). Keys computed at
runtime (validation messages carried by Zod schemas, API error codes) go through the single
helper `tKey(t, key)` in `apps/admin/src/lib/errors.ts`. Form schemas use translation keys as
their messages (e.g. `common:validation.required`).

## Admin portal

- API refusals carry a machine reason (`details.reason`, e.g. `ESCALATION`, `LAST_OWNER`,
  `HUB_HAS_PAYMENTS`); the portal shows `admin:reasons.<REASON>` when it has one
  (`useAdminErrorText`), otherwise the error code's message.
- Permission labels follow the catalog key (`admin:permissions.orders.view`), so the role matrix
  needs no list of its own; `apps/admin/src/lib/permission-groups.test.ts` checks every key is
  grouped once.
- Lists that span locations show times in each row's location timezone; codes, numbers, e-mail
  addresses and raw data (audit details, sync payloads) are shown left-to-right inside Arabic.

## Customer website

- The site follows the visitor's stored choice, else the browser language, else English
  (`initialLocale`), and remembers a change in localStorage.
- Free-text from the restaurant reaches customers only as codes: reject reasons are stored as
  `TOO_BUSY`, `ITEM_UNAVAILABLE`, … and translated under `customer:status.cancelReason.*`; staff
  free text shows the generic `OTHER` message.
- Lists of options are joined with the locale's separator (`, ` / `، `); quantities and phone
  numbers are wrapped in `<bdi dir="ltr">` / `.ltr-nums`.
- Times (acceptance deadline, opening hours) are shown in the location's timezone with
  `formatTime`.

## Signed amounts

Show surcharges with `formatMoney(amount, currency, locale, { sign: 'exceptZero' })`, which lets
`Intl` place the sign for the locale. Never concatenate `"+" + price`: it breaks in RTL.

## Fonts

Apps bundle fonts locally (`@fontsource-variable/inter`, `@fontsource-variable/noto-sans-arabic`).
The POS works offline, so fonts must never come from a CDN.
