# MADAR multi-tenant expansion: migration plan

## Context

The repo (`restaurant-platform`, pnpm/turbo monorepo) is a finished offline-first restaurant platform: Phases 0–10 merged (up to PR #10). The goal is to turn it into **MADAR (Powered by JudyTech)**, a multi-tenant, modular commerce platform for restaurants, cafés, supermarkets, clothing and retail stores. It stays one codebase, and all behaviour is driven by configuration and capabilities, never forks.

Decisions taken with the product owner: **development only** (no live data, so no long-lived compatibility shims); **full rename** Restaurant → Tenant, all the way through DB, code and routes; **separate platform-admin app with its own identity**.

Working rules: one branch and PR per phase, cut from `main`. Each phase stops for review before the next begins. Each phase gate runs `pnpm build typecheck lint test`, `pnpm e2e`, `pnpm test:tools`, `migrate status` and the hub schema contract test, then updates the docs. Each phase also gets its own ADR (0017–0026).

Internal package scope `@pos/*` stays (not user-visible; a rename is pure churn).

## Configuration precedence (applies to features, theme and settings)

`Platform defaults → Business-type defaults → Tenant → Location → Device`. More specific wins. A **platform entitlement** sits above all of them: a tenant can only enable modules the platform allows. One pure resolver, `resolveLayered()` in `packages/domain/src/config/`, implements this and is documented in a new `docs/configuration.md`.

## Phase 2 — Feature/module system (ADR 0018)

- **Catalog:** `FEATURES` in `packages/shared-types/src/features.ts`: POS, KDS, KITCHEN_PRINTER, ONLINE_ORDERING, BARCODE, INVENTORY, TABLES, MODIFIERS, PRODUCT_VARIANTS, DELIVERY, SELF_CHECKOUT, CUSTOMER_DISPLAY, LOYALTY, ADVANCED_REPORTING.
- **Defaults:** `BUSINESS_TYPE_DEFAULTS` in `packages/domain/src/features/defaults.ts`, following section 5: restaurant, coffee shop (POS, KDS, MODIFIERS, ONLINE_ORDERING, SELF_CHECKOUT), supermarket/grocery, clothing/retail, other. The resolver `resolveFeatures(layers)` is built on `resolveLayered`.
- **Data:**
  - `TenantEntitlement` (tenantId, feature, entitled, tenantConfigurable): set by the platform.
  - `FeatureOverride` (tenantId, locationId?, deviceId?, feature, enabled): set by tenant admins, only for configurable features.
  - Both ride the snapshot and get change-feed triggers, so the hub enforces them offline.
- **Server:**
  - `FeatureService.isEnabled(feature, scope)`, cached per request.
  - `@RequireFeature(F.KDS)` decorator and guard: kitchen routes need KDS, floor routes TABLES, online ordering ONLINE_ORDERING, and so on.
  - The route inventory records each route's feature. The security test walks every feature-gated route and expects `403 FEATURE_DISABLED` when the feature is off.
- **Domain behaviour driven by capability, not type:**
  - With KDS off, confirmed orders create no kitchen tickets and can be completed directly.
  - With TABLES off, `DINE_IN` doesn't require a table.
  - With MODIFIERS off, modifier groups are hidden from the published menu.
- **Context API:** `GET /tenants/:tenantId/context` returns resolved features, branding, currency and locales. It is served by cloud and hub. `TenantProvider`, `useFeature()` and `<FeatureGate>` live in `packages/app-kit`.
- **UI guards:**
  - POS nav (tables), `cart-panel` table select, `options-dialog` modifiers, `kitchen-progress` and kitchen priority.
  - Admin nav items.
  - The KDS app shows "module disabled" when KDS is off.
- **Admin:** a "Modules" settings page (configurable features only, showing the inherited value and source).
- **Lint rule:** `pos-local/no-business-type-branching` forbids `businessType ===`/`switch` outside `features/defaults.ts` (section 27).
- **Tests:** enable/disable, business-type defaults, tenant/location/device override precedence, entitlement ceiling, guard 403s, UI gate component tests, hub offline enforcement.

## Phase 3 — Branding + theme (ADR 0019)

- **Platform branding:** `PLATFORM_BRAND` (MADAR · Powered by JudyTech, default assets) in `packages/shared-types/src/brand.ts`. It is the single source for the i18n `appName`, `<title>`s, Tauri `productName` "MADAR POS" (identifier `app.madar.pos`), the admin sidebar and login footers. A test fails if a component hardcodes the brand string.
- **Tenant branding:** `TenantBranding` (displayName en/ar, logo/favicon file ids, primary/secondary/accent, fontFamily, logoSize, themeMode, surfaceStyle `solid|glass`, borderRadius). Optional per-surface overrides (`login`, `pos`, `kds`, `kiosk`, `website`) are a JSON field validated by zod.
- **File storage:** a `TenantFileStorage` interface with a local-disk dev adapter (an object-store adapter later), and a `TenantFile` table. Keys are prefixed `tenants/<tenantId>/`. Logo and favicon uploads accept PNG/JPEG/WebP/ICO only (no SVG, to avoid script injection), with size and type checks. **Test:** tenant A cannot read or overwrite tenant B's files.
- **Design tokens:** restructure `packages/ui/src/styles/theme.css` into semantic tokens with `[data-theme=dark]` (the default: a premium charcoal/black palette with soft borders, restrained gradients, an optional subtle glass surface and high contrast), `[data-theme=light]`, and system mode through `prefers-color-scheme`.
  - `applyTenantTheme()` in app-kit writes tenant colours into CSS variables and computes readable foregrounds. A contrast check rejects unreadable combinations at save time, in the domain/ui util.
  - `ThemeProvider` supports LIGHT/DARK/SYSTEM, using device preference over the tenant default.
  - The KDS hardcoded `class="dark"` is removed.
- **Lint rule:** `pos-local/no-raw-colors` forbids palette classes and hex values outside the token files and receipts.
- **Tests:** theme switching, tenant token application, RTL/LTR with branding, contrast validation, and component snapshots per theme.

## Phase 4 — Currency + localization (ADR 0020)

- Add ILS (2) and others to the exponent table.
- `CurrencyConfiguration` = `{ currencyCode, symbol override (₪ default for ILS), display (narrowSymbol/code), decimalPlaces (from ISO, read-only), formatLocale }`. Tenant columns, resolved in the context API.
- `formatMoney` takes the configuration. New tenants default to **ILS**.
- Remove the `'SAR'`/`Asia/Riyadh` fallbacks. Seed: ILS, `Asia/Hebron`.
- **Locales:** `supportedLocales`/`defaultLocale` drive the language switcher (it shows only supported locales). Initial locale: stored preference (if supported) → user `preferredLocale` → tenant default. Single-locale tenants hide the switcher. An optional Arabic-Indic digits setting.
- **Tests:** ILS/USD/EUR/JOD(3)/GBP formatting in ar and en, and minor-unit round trips. No float math, which the existing ADR 0002 lint and tests cover. Also RTL/LTR per supported-locale set.

## Phase 5 — Retail capabilities (ADR 0021)

- **Generic variants:** `ProductOption` (axis such as Size or Color, localized), `ProductOptionValue`, and `ProductVariantOptionValue`. `ProductVariant` gains `sku`, `cost`, `trackInventory` and images (`ProductImage` → `TenantFile`). Existing name-only variants stay valid (no option values required); nothing clothing-specific.
- **Barcodes:** `ProductBarcode` (tenantId, productId, variantId?, code, symbology `EAN13|EAN8|UPC_A|CODE128|OTHER`, isPrimary), unique `(tenantId, code)`. EAN/UPC check digits are validated in `@pos/domain`. `OrderItem` gains `sku`/`barcode` snapshots.
- **Lookup:** `GET /locations/:lid/catalog/lookup?code=` on cloud and hub (BARCODE feature). The published menu carries barcodes so the POS can look them up locally, offline.
- **Scanner abstraction** in `packages/app-kit/src/scanner/`:
  - A `ScannerSource` interface.
  - `KeyboardWedgeScanner`: detects HID bursts ending in Enter, with configurable timing, and does not swallow normal typing.
  - `ManualEntry`.
  - A `NativeScanner` placeholder for a later Tauri/WebHID integration.
  - A `useBarcodeScanner` hook. The POS adds the scanned variant to the cart; an unknown code shows a toast.
- **Admin:** a product editor with options, a generated variant matrix (size × colour), per-variant SKU/barcode/price/cost, and barcode entry.
- **INVENTORY:** only the `trackInventory` flag is added now. A stock ledger is a separate phase, flagged as out of scope.
- **Tests:** barcode lookup (product and variant), checksum validation, duplicate barcodes within a tenant refused (allowed across tenants), variant lookup and pricing, scanner burst detection, offline lookup on the hub.

## Phase 6 — Self-service kiosk (ADR 0022)

- **Terminal devices:** pairing generalizes from `GATEWAY` to `POS/KDS/KIOSK/CUSTOMER_DISPLAY` against the hub, with a pairing code shown in the admin. `DeviceType.KIOSK` is added. This also supplies the "device" configuration layer and the version reporting used in Phase 10.
- **`apps/kiosk`:** a touch-first React app served like the KDS. It is a hub LAN client, so it works offline. It authenticates as a kiosk device with a narrow principal (menu read, self-service order create, payment intent, nothing else). Idle reset, attendant exit by staff PIN, and accessibility.
- **No duplicated logic:** `POST /locations/:lid/kiosk/orders` is a thin controller over the existing `OrdersService` and pricing engine, with new channel `KIOSK` and source `KIOSK`.
  - Restaurant flow: paid at the kiosk → `CONFIRMED` (kitchen tickets if KDS is on). "Pay at counter" → `PLACED` until a cashier takes payment.
  - Retail self-checkout flow: scan → cart → pay → `COMPLETED`.
- **Payments:** a `PaymentTerminalProvider` interface (integrated card terminal) with a mock adapter. The CHECK constraint is relaxed so drawer-less payments are allowed for kiosk card payments, not only `ONLINE`.
- **Tests:** a kiosk order reaches the KDS; a retail checkout completes a sale; a kiosk device is refused on staff routes (walked from the inventory); SELF_CHECKOUT off → 403. E2E: kiosk → hub → KDS.

## Phase 7 — Multi-tenant website (ADR 0023)

- **`TenantDomain`** (id, tenantId, domain unique, kind `SUBDOMAIN|CUSTOM`, isPrimary, status `PENDING|VERIFIED|FAILED|DISABLED`, verificationToken, verifiedAt, createdAt).
  - `<slug>.madar.app` is auto-verified (`PLATFORM_WEB_DOMAIN`).
  - Custom domains are verified by a DNS TXT record (`_madar-verify.<domain>`) through a mockable `DomainVerifier`.
  - **Only VERIFIED domains resolve.**
- **Resolution:** a `HostTenantGuard` resolves `Host` (`X-Forwarded-Host` only behind `TRUST_PROXY`) → tenantId and sets the tenant context. It is a new route-inventory class, `host`.
  - Public routes become `/public/site`, `/public/site/locations/:id` and `/public/site/menu`. `POST /orders` and tracking now check that the location belongs to the resolved tenant.
  - Any tenant id or slug the browser sends is ignored.
- **Hosting:** the website and its `/api` are served same-origin through the reverse proxy, which avoids per-domain CORS. An infrastructure example uses Caddy on-demand TLS with an `ask` endpoint, `/internal/domains/check`, so certificates are issued only for verified domains. Dev uses `<slug>.localhost:5175`.
- **Website config:** `WebsiteConfig` (tenantId, draft + published JSON, version, publishedAt), validated by a zod discriminated union of sections: Hero, FeaturedProducts, Categories, About, Gallery, Testimonials, Locations, Contact, OpeningHours, PromoBanner, Footer, plus navigation, social links and SEO. Each section has {id, type, enabled, order, localized content, appearance}.
- **customer-web:** a section-renderer registry, with tenant branding and theme applied before render.
- **Admin:** a website editor (toggle, reorder, edit, preview draft, publish) and a domain settings page.
- **Tests:** hostname → tenant, custom domain → tenant, unverified, disabled or unknown domain → 404, tenant B's location through tenant A's host → 404, a cross-tenant order refused, a forged tenant header ignored, section schema validation, and a renderer component test.

## Phase 8 — Payment configuration (ADR 0024)

- **`PaymentProviderAccount`** (tenantId, locationId?, method, providerKey, mode `TEST|LIVE`, publicConfig, status) plus a **cloud-only** `PaymentProviderSecret` (`/// @cloud-only`, never in the hub snapshot). `PaymentMethod` links to an account.
- **`SecretBox`:** AES-256-GCM envelope encryption, key from `PAYMENT_SECRETS_KEY` behind a `KeyProvider` interface (KMS later), AAD = tenantId+accountId so a ciphertext cannot move between tenants. Secrets are write-only in the API; responses show only `hasSecret` and a fingerprint. Redaction is extended.
- **Provider selection:** a `PROVIDER_CATALOG` (key → adapter + zod config schema) replaces the static registry and the global env var. `PaymentProviderFactory.forTenant(tenantId, method)` picks the adapter. Cash-only tenants simply have no ONLINE account.
- **Tests:** per-tenant provider selection, a cash-only tenant refused online checkout, secrets absent from every response, log, audit and snapshot, ciphertext swapped between tenants refused, key rotation.

## Phase 9 — Platform admin (ADR 0025)

- **Identity:** `PlatformUser` (role `OWNER|OPERATOR|SUPPORT|VIEWER`), `PlatformRefreshToken`, token audience `madar-platform`, cookie path `/api/v1/platform/auth`.
  - The tenant `AuthGuard` refuses platform tokens and vice versa.
  - A platform permission catalog and `PlatformGuard`, with route-inventory class `platform` and the boot check.
  - The first owner is created by CLI (`pnpm platform:create-owner`); there is no signup.
- **API** `/platform/*`:
  - Tenants: list, search, provision through `TenantProvisioningService`, status (suspend → tenant and hub requests refused with `TENANT_SUSPENDED`).
  - Locations, users and devices (read).
  - Entitlements, branding, domains (verify), payment accounts (secrets never revealed).
  - Health: devices online/offline by `lastSeenAt`, sync pending (hub-reported outbox) and failed (`ProcessedOperation`), last sync, recent errors from a new `PlatformErrorEvent` table written by the exception filter for 5xx responses.
  - Audit logs: tenant and platform.
- **Support tools:** a `SupportOperation` catalog. Each operation has a `preview()` returning tenant, entity, before and after, and an `execute()` that requires the preview's confirmation token (a hash of the before-state, short expiry), a reason, and a role. Each execution writes platform and tenant audit rows. The operations:
  - Find order, customer, product, payment or sync operation.
  - Retry sync and reprocess failed operations, reusing ADR 0014's APPLY_HUB/RESEND resolution.
  - Correct order status through the domain state machine as SYSTEM, with no bypass of the money guards.
  - Correct product mapping (the snapshot is untouched).
  - Recalculate totals: open orders only; a finalized order gets a diff report, never a silent change.
  - Restore an archived entity.
  - No SQL console.
- **`apps/platform-admin`:** same `@pos/ui`, MADAR brand, en/ar RTL. Pages: tenants, tenant detail tabs (locations, users, devices, modules, branding, domains, payments, health, audit), support tools, health board.
- **Tests:** every `/platform` route refuses tenant tokens and anonymous calls (walked from the inventory); SUPPORT can read but not repair; repairs without confirmation or reason are refused; audit rows carry before/after; a suspended tenant is locked out.

## Phase 10 — Deployment/version management (ADR 0026)

- **Single version:** the root `package.json` holds the MADAR version (e.g. `1.0.0`). `tools/release/set-version.mjs` stamps all apps, Tauri and Cargo.
- **Version reporting:** Vite `define` exposes `MADAR_VERSION`. `/health` returns the version. Clients send `x-madar-client-version`. The hub heartbeat and paired terminals report theirs into `Device.appVersion`/`lastVersionAt`.
- **Release tracking:** `Release` (version, channel, notes, publishedAt, minSupportedHubVersion/clientVersion) and `TenantReleaseChannel` (STABLE/BETA/pinned) for controlled rollout tracking. The cloud refuses hubs below the minimum with a typed error; this also closes the snapshot schema-skew risk found during mapping.
- **Platform admin "Releases" page:** device versions per tenant and outdated devices.
- A CHANGELOG, and `docs/release.md` updated.
- **Tests:** version stamping, minimum-version refusal, device version recorded.
